# PREF-0001 — Never solve a design problem by lowering ambition

**Polarity:** reject
**Facet terms:** governs all facets; not bound to any single term
**Scope:** all work, design included
**Evidence:** Sam had a graphics-settings downgrade reverted in the Zero Hour mod — original high settings restored and the particle ceiling raised instead — and drove the pivot from INI hacks to a full source build rather than accept the engine's limits (2026-08-13)
**Date:** 2026-08-13

**The preference.** Do not offer reduced quality, scope or ambition as the solution to a
design problem. Name the actual constraint, say whether it can be lifted and what lifting it
costs. If it genuinely cannot be lifted, say so plainly.

**Why.** A downgrade solves *my* problem — making a metric move, making a layout resolve —
rather than Sam's. It reads as missing the point rather than as a fix. An honest "this is a
hard limit" is wanted; a quiet reduction presented as a solution is not.

**How this applies to design specifically.** Dropping a feature from a screen because the
layout is hard, simplifying a chart because the data is awkward, cutting a state because it
is tedious, or going sparse because density is difficult — all of these are this failure
mode wearing design clothes. Solve the hierarchy problem instead, or name it as unsolved.

**Exceptions.** A reduction driven by a *named external constraint* — bandwidth, legality,
platform capability — is not a downgrade. It is a documented trade, and it belongs in a DDR
with its cost written down.
